## 我要作的决定

簡繁与异体的映射数据从哪来。

**为什么现在问**：issue #4 的手写小表跑通了 15 条黄金查询（召回 100%），
但它只覆盖 `queries.tsv` 用得到的 6 个字。`vault/raw/` 一进真实文件，**表外字就是绝大多数**——
而表外字符的行为是「原样匹配」，也就是**退回 rg 的 50%**。这张表往下怎么长，决定 42find 能不能出玩具语料。

## 一、这件事上，我不可妥协的是哪几条

| # | 不可妥协的 | 为什么它是命门 | 怎么算满足 |
|---|---|---|---|
| 1 | **许可能与 MIT 二进制共存，且覆盖的是「数据」不只是「代码」** | 意向书要的是「一个能装到别人机器上的 `42find` 二进制」。许可脏就不能分发——这不是风格问题，是这个作品存不存在的问题。词典数据常与代码分属不同许可（代码 Apache-2.0、数据 CC-BY-SA 之类），**只看仓库根目录那个 LICENSE 会看漏** | 数据文件本身明载 MIT / Apache-2.0 / BSD / CC0 / Unicode License 之一，且能指出是哪个文件覆盖了 `data/` |
| 2 | **纯 Rust、构建期内嵌，运行期零外部文件、零 C 依赖** | 同一个理由的另一半：要 `libopencc` 就要用户先装 C 库，要外部词典文件就不是「一个二进制」。`opencc-rust` 已因此在 §2 出局 | `cargo build --release` 出来的单个二进制，在**空目录**里能跑出正确的簡繁互查，`otool -L` 不含第三方动态库 |
| 3 | **能抽出「字符 → 变体集」的非对称关系，而不只是「把这段文本转过去」** | **这一条最可能全军覆没。** 本轮已证等价「类」是错的抽象（对称传递会让查「發」命中「髮」）。而现成 crate 全是**转换器**（`convert(&str) -> String`）——转换器只给你一个方向的结果，给不出「发 → {發, 髮}」这张关系。给不出，就只能自己从原始词典反推 | 能写出 `fn variants_of(c: char) -> &[char]`，且它对「发」返回两个字、对「發」不返回「髮」 |

## 三、哪些看起来相关，但知道了也不改变这个决定

**排除项。一条不看的，抵十条要看的。**

- **词组级转换质量**（`干/幹·乾`、`里/裡` 这类要看上下文的）——本刀做的是字符级，词组歧义已划给真难题②的尾巴。候选在这方面强不强，不改变本决定。
- **地区词转换**（软件/軟體、鼠标/滑鼠）——那是**翻译**，不是字形归一。意向书的承诺是「rg 因**字形差异**漏掉的那些」，不是词汇差异。
- **转换速度 / benchmark**——表是构建期的事，运行期只是查表。何况本项目的延迟数字在真实语料到位前本来就不作数。
- **日文新旧字体、韩文汉字**——本刀范围外（issue #4 已划）。
- **CLI 工具好不好用 / 有没有 Python 绑定 / WASM**——我要的是数据，不是它的包装。
