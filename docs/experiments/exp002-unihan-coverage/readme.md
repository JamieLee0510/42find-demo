# exp002 · Unihan 变体表在真实查询词上覆盖到什么程度

## 假设

`docs/research/001_variant-table-source/decision.md` 把这条列为「仍未补齐的那一处」：
Unihan 那 12,972 字**在真实语料上的命中率没有数**。同时 `docs/plan/001` 的待拍板第 1 条
给了一个**没实测过的建议**：「`kSemanticVariant`(3538) 建议默认不进（最伤精确率）」。

**待验假设**：
1. 用 `kSimplifiedVariant` + `kTraditionalVariant` 两个主字段，真实查询词的簡繁互查基本够用。
2. 加进 `kSemanticVariant` 等附加字段会**伤精确率**，所以默认不该进。

## 做法

- **真实依赖，不是模拟**：直接读 `resources/unihan-database/` 的一手数据文件
  （Unicode License V3，`clone.sh --depth 1`，最近提交 2026-07-24）。
- **展开规则与产品代码一致**：`probe.py` 的 `expand_char` 逐条对应 `src/42find-core/src/expand.rs`
  ——非对称，变体只回连规范形。
- **样本先定死再跑，20 个**：真实场景里会敲的查询词。
  **故意放进预期会失败的**——地区词（软件/網路/資料庫）不是字形问题、意向书已划出范围，
  但真实用户一定会撞上，所以要量出来而不是回避。
  ground truth 是「该词在一份繁体文档里实际的写法」，两地写法不同的**两个都列**。
- **两个方向都测**：简体查繁体、繁体查简体。
- **四种字段组合各跑一遍**，且**每种都记代价**（两条非对称钉子 + 平均展开集大小）。

跑法：`python3 docs/experiments/exp002-unihan-coverage/probe.py`

## 结论

### 逐条结果（模式 A = 当前实现）

| 查询 | 简→繁 | 繁→简 | 判读 |
|---|---|---|---|
| 检索 / 后台 / 面条 / 系统 / 用户 / 冲突 / 划分 / 复制 / 历史 / 制作 / 钟表 | ✅ | ✅ | **能**：常规簡繁与一对多都过 |
| 头发 → 頭髮 | ✅ | ✅ | **能**：一对多的钉子，两个方向都对 |
| 里面 → 裡面 · 裏面 | ✅✅ | ✅✅ | **能**：一简对两繁，两个都命中 |
| 台湾 → 臺灣 · 台灣 | ✅✅ | ✅✅ | **能** |
| 只有 → 只有 | ✅ | ✅ | 能 |
| 只有 → **祇有** | ❌ | ❌ | **不能**：`祇` 只在 `kSpecializedSemanticVariant` 里 |
| 干净 → **乾淨** | ❌ | ❌ | **不能**：见下「一个反直觉的失败」 |
| 数据库 → 資料庫 · 网络 → 網路 · 软件 → 軟體 | ❌ | ❌ | **不能，且不该能**：地区词是**词汇**差异不是字形差异，意向书已划出范围 |
| 发布 → **發佈** | ❌ | ❌ | **不能**：`布`/`佈` **在 Unihan 的任何一个变体字段里都不存在**（全字段扫过） |

### 四种字段组合

| 模式 | 字段 | 简→繁 | 繁→简 | 词级可用 | **钉子守住？** | 平均展开集 |
|---|---|---|---|---|---|---|
| **A** | `kSimplified` + `kTraditional`（当前实现） | 21/27 | 21/27 | 19/20 | ✅ | 2.43 字 |
| **B** | A + `kSemantic` + `kSpecializedSemantic` + `kZ`（仍一跳） | **22/27** | **22/27** | 19/20 | ✅ | 2.76 字 |
| C | A 的两跳传递闭包 | 21/27 | 21/27 | 19/20 | ❌ **破** | 2.67 字 |
| D | B + 两跳 | **23/27** | **23/27** | **20/20** | ❌ **破** | 3.48 字 |

「钉子」＝ `expand(發)` 不含 `髮` 且 `expand(髮)` 不含 `發`，即决策二的非对称。

### 一个反直觉的失败：干净 → 乾淨

失败的不是「干」，是「净」：

```
净 → kTraditionalVariant → 凈 (U+51C8)      ← Unihan 只走到这里
凈 → kSemanticVariant    → 淨 (U+6DE8)      ← 真实繁体文档写的是这个
```

**「净 ↔ 淨」隔着两跳**，而两跳正是决策二明确拒绝的那一步（charabia 也拒绝，
`resources/charabia/irg-kvariants/src/lib.rs:126-142` 的 `test_no_loop`）。
模式 D 能修好它，代价是两条钉子都破。

### 一个 bug —— 在我这边，不在数据那边

初版探针写的是 `if c in TRAD: ... elif c in SIMP: ...`。
`裡` **同时是两个文件的 key**（`kTraditionalVariant` 指向自己、`kSimplifiedVariant` 指向 `里`），
自指条目被剥掉后 key 仍在，`elif` 被短路——**反向映射被静默吃掉**，`裡面` 查不回 `里面`。
改成并集即修好（繁→简 20/27 → 21/27），且**并集不破坏非对称**：
`expand(發) = {發} ∪ TRAD[發]{} ∪ SIMP[發]{发}`，仍不含 `髮`。

⚠️ **这个 bug 现在还没在 Rust 里暴露**：`src/42find-core/src/expand.rs` 也是 `if/else if`，
但手写小表里一个字要么是 key、要么在 value 里，从不同时是两者。
**换成 Unihan 的那一刻它就会现形。** 决策三落地时必须一起改成并集。

## 这条结论改变了什么取舍

1. **推翻了 `docs/plan/001` 待拍板第 1 条的建议。** 原话是「`kSemanticVariant` 建议默认不进
   （最伤精确率）」——**实测不成立**：模式 B 净赚一条（`祇有`），**两条钉子都守住**，
   展开集只从 2.43 涨到 2.76 字。**它不伤精确率，该进。** 那句「最伤精确率」是我凭直觉写的。
2. **决策二「拒绝传递闭包」得到实测支持，理由却换了。** 原理由是「等价关系的对称传递会让
   假阳性从后门溜回来」——对，但更实在的理由是：**模式 C 一个都没修好，纯亏损。**
   模式 D 确实能修好两条（`祇有`、`乾淨`）、把词级做到 20/20，但**打破非对称**
   （`expand(發)` 变成 `發发髮`）。取舍变成一句话：**多两个词，还是守住不查错。**
   这一句现在有数字撑着，可以交给人拍板了。
3. **给「精确率补不补成第三个数」添了一条依据**（`plan/001` 待拍板第 3 条）：
   B 与 D 的差别**只在精确率上**，召回都涨。不量精确率，就没有依据在 B 和 D 之间选。
4. **`布`/`佈` 这类够不着的，划进范围外要有出处**：不是「暂时没做」，是
   **Unihan 全部六个变体字段里都没有这条关系**，属于用字习惯而非字形变体。

## 边界

- **规模边界**：20 个查询词、27 条 ground truth。只够回答「这些词能不能」，
  **不能外推成覆盖率**——真实语料上的字频分布没测，`vault/raw/` 还是空的。
- **ground truth 边界**：繁体写法由人写、按常识判定，**没有语料统计支撑**。
  两地写法不同的取了两个，但没有加权（哪种更常见没测）。
- **时间边界**：`unicode-org/unihan-database` @ 2026-07-24。
  `kSimplifiedVariant` / `kTraditionalVariant` 在 [UAX #38](https://www.unicode.org/reports/tr38/)
  里是 **provisional 字段**，Unicode 有权改。
- **未测**：全半角（走的是整块偏移规则，不经变体表）· 日文假名与新旧字体（范围外）·
  展开集变大对**查询延迟**的影响（要等索引，现在是朴素扫描，量不出差别）。
- **未测的代价面**：模式 B/D 的假阳性只用两条钉子代表，**没有在真实语料上统计过误命中**——
  那要等 `vault/raw/`。
