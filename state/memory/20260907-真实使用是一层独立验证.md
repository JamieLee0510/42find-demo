# 评审全绿不等于能用；玩具语料会把 bug 藏住

## 为什么

2026-09-07，PR #6 合并进 main、CI 第一次跑就绿。那之前它过了 **十三个评审视角**：
六轮双谱系评审 + 四视角 `/simplify` + `pr-ready` 三视角。

**合并完拿 45,624 字节真实中文自己跑第一遍，出了三个问题**（issue #7）：

1. 输出只给命中的那个词、不给整行——搜到了却看不到上下文，得再打开文件。
   `rg` 三十年前就是 `路径:行号:整行`。**十三个视角没有一个提过。**
2. 同一行两处命中，不带 `--column` 时输出两行**逐字节相同**的结果。
3. `42find … | head` **panic 退 101**，而 `--help` 只承诺 `0/1/2`。

三条都不是「代码写错了」，是**「这东西拿来用会怎样」**。评审读的是 diff，
问的是「这段代码对不对」；没有人去敲一遍 `42find 词 | head`。

**第三条还多一层**：它其实一直在，但**固定语料只有 10 行输出**，在 `head` 退出前
就全进了管道缓冲，退出码是 0。换 2012 行真语料才炸出来。
**玩具语料不是「小一点的真语料」，它是另一种东西**——它把与规模相关的失败模式整类藏住。

同一天还有一条同形的：`state/memory/20260906-管道退出码.md` 讲的是判命令成败时管道会吞掉退出码；
这次是**程序自己写那一侧**吞掉写失败（全仓 0 处 `flush`）。
这个项目在**读**那一侧花了好几轮消灭「静默假阴性」，换到**写**那一侧一处都没做。
见 [[pipe-exit-code]]。

## 怎么用

- **交付前必须有「自己用一次」这一步，它是独立的一层，不能被任何数量的评审替代。**
  写进验收清单，不靠记性。
- 用的材料要**真实且够大**：真实的内容（不是为测试造的）、真实的规模（能触发缓冲、
  分页、超时的那个量级）。测试语料与真实语料**都要跑**，不能只跑前者。
- **最常见的几种用法要各敲一遍**，尤其是把工具接进管道：
  `| head` · `| less` · `| grep -m1`（这三种会断管道）· 重定向到文件 · 无命中 · `--help`。
  每一种都**单独看退出码**（别接管道判，那会拿到管道末端的码）。
- **对照物要真的跑**：拿同类成熟工具（这里是 `rg`）在同一份材料上跑同一件事，
  把两边的输出摆在一起看。「形态不一样」往往就是问题所在，而形态问题在 diff 里看不出来。
- 能变成规则的立刻变：这次「不许用 `println!`/`eprintln!`」已升成 `Cargo.toml` 里的
  `clippy::print_stdout` / `print_stderr = "deny"`，跑在既有闸门里（CLAUDE.md 第三节）。
  **但「输出形态好不好用」判不了，它就是验证红线，留给人。**
